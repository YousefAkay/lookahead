# Ask, spec (2026-11-20)

## What it is
I type a question about my money in plain English or French, and Lookahead answers it. When I turn on the optional LLM (Claude Haiku 4.5, off by default), it sees only my question, the fixed category list and the plan format. It writes a plan of building blocks without seeing any result. Lookahead checks the plan, runs it on my machine with the code it already has, and shows the answer with "How I worked it out", so I can tell when it misunderstood me. Without the LLM, an offline parser answers the simplest questions.

## Changes from HANDOFF section 11
Recorded here, and in DECISIONS with the first commit:
- **Cloud model, opt-in, instead of a local Ollama default.** Haiku 4.5 at temperature 0, off by default. Ollama is not used.
- **No retrieval-augmented explanation mode.** HANDOFF planned a mode where the LLM writes answers from retrieved alerts and transactions. I dropped it: nothing computed is ever sent to the LLM, and every answer sentence is built by code from computed numbers. "Why did you warn me?" stays with the evidence card I already have (Needs a look).
- **A plan of building blocks instead of one fixed query form.** Multi-step plans are allowed, and later steps can use earlier results by name.
- **Merchant names are matched locally,** never sent.
- **A bigger test set:** 200 development and 100 held-out questions, instead of about 40. They are scored on whether the computed answer is right, plus refusals and asking back. The planned faithfulness score is dropped, because no answer text is written by an LLM.
- **Less risk from transaction descriptions:** the LLM never sees them, so an instruction hidden in a description cannot reach it.

## Decisions
- **Building blocks** (1a). Each step has a name; the result is in brackets.
  - `rows`: filter by category, merchant, period, amount range, money in or out, kind (income, bill, everyday, transfer, refund) [rows]
  - `group`: by month, week, category, merchant or weekday [table]
  - `aggregate`: sum, average, count, max, min over rows or a table [number]
  - `top`: top or bottom N of a table [table]
  - `compare`: difference, % change, share of [number]
  - `list`: rows, largest or latest first [rows table]
  - `forecast`: balance on a date, lowest balance in a window, chance below the buffer or an amount [number and range]
  - `whatif`: spend more or less in a category per month, cancel a recurring payment, swap one for another amount, add a one-off. Same engine as the Scenario page [before/after lowest balance and chance]
  - `budget`: one category or all [limit, spent, likely end, chance over]
  - `safe_to_spend`: same figure and sentence as Home
  - `recurring`: list my recurring payments, or find one by name [table with next date and usual amount]
  - `cannot_answer`, with a reason; `clarify`, with a question back
  - Why: it covers lookups, comparisons, forecasts and what-ifs with few, well-tested pieces; `recurring` is needed for "cancel X".
- **Plan checks** (2a):
  - at most 10 steps; a step uses only names defined before it; the types must fit
  - unknown fields are refused, and categories come from the fixed list
  - periods are words or months ("last_month", "2025-03") turned into dates locally, so the LLM never sees today's date or my data's range
  - forecast dates are capped at 30 days past the end of my data; top N at 25; listed rows at 200
  - one automatic retry on a failed check, sending back only the error, never data (tested: no amounts, dates, balances or merchant names from the data)
  - the question is sent as I typed it; when the LLM is on, the page says "Your question is sent as you typed it"
  - "How I worked it out" is generated from the checked plan by code, never written by the LLM
  - Why: a wrong plan fails loudly instead of answering silently, and the explanation cannot misdescribe what ran.
- **Merchants** (3a): the LLM copies the phrase as I wrote it. Lookahead matches it locally: exact, then alias, then cleaned spelling, then a close match. Several close matches → buttons to pick one. None → "No merchant like '…' in your data." Merchant names are never sent. Why: privacy, and one configuration to score.
- **Ambiguity** (4a): best guess, shown plainly, from written defaults:
  - "last month" = the previous full calendar month
  - "this year" = January 1 to today
  - "spending" = money out, without transfers or refunds
  - a word that is neither a merchant nor a category goes to the closest category, labelled as such ("coffee" → Restaurants & cafés, closest category)

  It asks back only when a guess would likely be wrong: close merchant matches, or no clear subject. Why: fast answers, and the misreading is always visible.
- **LLM off** (5a): an offline keyword parser in English and French covers about 8 simple shapes:
  - total or average for a category or merchant over a period
  - balance on a date
  - chance of a dip
  - safe to spend
  - budget for a category
  - top categories in a period
  - list my recurring payments

  Clickable example questions are shown too. It builds the same plans, so answers look identical. Why: it is cheap, it works offline, and it is the baseline the LLM must beat.
- **What I see** (6a): a new top-level section, "Ask". It has a text box, then:
  - an answer sentence built by code from the computed numbers
  - the number or table
  - "How I worked it out": numbered plain-words steps and the merchant matches made
  - "Rows behind this"
  - "Data through <date>"

  Answers are in English even for French questions. Each question stands alone: there are no follow-ups ("and last month?"). Questions are not stored.
- **Test set size and coverage** (7a): 200 development and 100 held-out questions. Each is tied to one development persona and a fixed "today"; held-out personas are never used. Each set aims at:
  - about 50% answerable lookups (single and multi-step, top N, comparisons, typos, informal wording)
  - 15% forecast and what-if
  - 10% budget and safe-to-spend
  - 10% ambiguous
  - 15% should-refuse (advice, opinions, not in my data, past the 30-day horizon)
  - about 15% in French
- **Who writes the questions, and how held-out stays unseen** (8a, my change):
  - Development (200): written while building Ask (not by me).
  - Held-out questions (100): written by two independent fresh subagents, 50 each, each with no access to the LLM prompt, the development questions or the other's 50, both from the persona sheet and the coverage targets. The second one writes in a different voice (casual student wording, short questions, typos, slang, about 7 in French). (My change, 2026-11-21: I no longer write 50 myself. Earlier plan: I write 50 in my own words.)
  - My role: reviewing the gold-plan disagreements and the 10 agreed plans chosen at random, one letter per case (A, B, or X with one line; OK or X for the spot checks). A fresh fixer subagent writes the corrected plan for each X from my line.
  - Held-out gold plans: two separate fresh subagents each write gold plans for all 100, independently. A script runs both plans for each question. Where the answers differ, it writes both in plain words into a file in the held-out folder (2026-11-21: it prints only a line count, so no route that runs it shows content to an agent), and I review only those, picking A, B, or a corrected version I describe. The same file also holds 10 gold plans where both agreed, chosen at random with a fixed seed set in a commit before I see any, for me to check.
  - The held-out folder is git-ignored and blocked by a hook for the coding session, the reviewer and every other subagent, the same way as `data/private/`. The subagents that write into it return only counts (the gold writers also a fingerprint), never content; I or the coding session take the set's fingerprint. The scripts that print from it are run by me.
  - Its SHA-256 fingerprint is committed before any scoring. The files are committed after the one scored run, so the result can be checked.
    - **2026-11-26:** published after the scored run in docs/results/ask_testset/: the 100 questions, gold A, gold B and the final gold, copied by `python -m tools.publish_ask_testset`, which refuses unless every file matches the fingerprint committed on 2026-11-25. My review files (review.txt, answers.txt, review_cases.json) stay unpublished.
  - The block code also has unit tests with answers worked out by hand on tiny fake data, because a gold plan run through the same code cannot catch that code's bugs.
- **Scoring and pass rule** (9a, my change). The rule is committed before any scored run.
  - "Correct" means the produced plan computes the same answer as the gold plan on the same persona and "today": numbers equal to the cent, same rows, same groups and values. Different but equivalent plans count as correct.
  - Question kinds come from the gold: **answerable** (the gold computes something, about 75), **ambiguous** (about 10), **should-refuse** (the gold is `cannot_answer`, about 15).
  - **Ambiguous questions:** asking back is correct when the gold is `clarify`. An answer from the written defaults is correct when it matches the gold. They are reported separately and are not in the correct-on-answerable rate.
  - **Silent wrong:** a computed answer shown (not a refusal, not asking back) that differs from the gold, counted over all 100 questions.
  - **Asking back on an answerable question:** not correct, and not silent wrong.
  - **Refusing:** only `cannot_answer` counts as a refusal (superseded by my readings below).
  - **My reading, 2026-11-20, decided before any held-out number exists** (it settles the line above and the step 3 note below):
    - A refusal is whatever the page shows as a refusal: `cannot_answer`; the offline parser giving no plan ("I can't answer that yet"); a local check refusing (a day past the forecast's 30 days, a day before the forecast starts, no budget set).
    - An API call that still fails after its retries is not correct, not a refusal and not silent wrong.
    - On answerable questions, a refusal is not correct and not silent wrong.
    - "Beats the offline parser by ≥ 20 points on correct-on-answerable" stays exactly as written. It is not revisited after seeing the held-out offline score.
  - **My readings, 2026-11-21, decided before any held-out question exists:**
    - **A plan that still fails its checks after the one retry is not a refusal.** It counts as not correct, not refused and not silent wrong, on every kind of question. The page says it with its own sentence, "I couldn't work that question out. Try asking it another way.", never the refusal sentence. Refusals stay exactly as above: `cannot_answer`, the offline parser giving no plan, and a local check refusing a valid plan (past the horizon, before the forecast, no budget set).
    - **Equivalence of one-value answers.** An answer that gives one value is compared by that value, to the cent, and the row it identifies, whatever its shape: a number taken from one row (max or min of rows) equals a list of exactly that one row. Example: "my largest purchase" as aggregate max, or as the largest 1 listed. A number that identifies no row (a sum, an average) never equals a list, and a list of two or more rows is compared row by row as before.
  - **Pass**, on held-out, with all four conditions:
    1. correct on answerable ≥ 85%
    2. bootstrap 2.5th percentile of that rate ≥ 75% (10,000 resamples of questions, fixed seed)
    3. refuses ≥ 90% of should-refuse questions
    4. silent wrong ≤ 5% of all questions, and the LLM beats the offline parser on correct-on-answerable by ≥ 20 points
  - **Run conditions:**
    - Haiku 4.5, the dated snapshot already used by the categorizer, temperature 0, one run.
    - A crash before any number is shown may be rerun. A single question whose API call still fails after its retries counts as not correct (and not silent wrong).
    - Every attempt goes in the ledger.
    - The offline parser is scored on the same held-out set in the same run.
    - Development runs are logged as development and are never scored against the rule.
  - **My readings, 2026-11-25, decided before the scored run:**
    - **A void attempt.** The attempt is void, with nothing scored, when the API refuses the key or account, the credit runs out, **5 questions in a row fail their API call**, the spending cap is reached, or the process crashes or is cut off before its result is recorded. Fewer than 5 failures in a row count against the planner as above.
    - **Another attempt needs my go,** recorded as a committed ledger line for the void attempt.
    - **Spending:** the run does not start with less than 1 USD left under the 5 USD cap.
    - **A result file left by a cut-off attempt** is not opened before my go; after it, the file is committed unopened or removed.
    - **A plan that makes the plan checker itself fail** counts as a plan that failed its checks, never as a crash.
    - **Disclosure:** the instructions for both gold-plan writers state that the single largest or smallest purchase is the maximum or minimum over rows. The LLM's instructions state the same convention, which came from its misses on development run 1. A maximum and a list of that one row count as the same answer, so I expect little effect. Only the "Conventions" section of the LLM's instructions was compared with the writers'.
  - **Result:** pass means the "Smarter questions" setting is offered (off by default). Fail means Ask ships offline-only and the setting is not offered, as with categorizer v2. Results are reported with n.
  - **Outcome (2026-11-26):** the scored run (attempt 1dbc6244) failed on condition 4a only (silent wrong 8 of 100); Ask ships offline-only and the setting is not offered (DECISIONS 2026-11-26, report docs/results/ask_final_result_1dbc6244.md).
- 2026-11-20, while building step 3: the `whatif` block uses the **Forecast page's what-if engine** (the same 500 futures run again with the change), not the Scenario page. The Scenario page is a calculator with no chance of a dip, so it could not give "before/after lowest balance and chance". A dollar cut in a category becomes a percent of my usual spending there (its average over the 13 weeks the futures draw from), said in a note.
- 2026-11-20, while building step 3: a refusal made by a local check (a forecast day past the 30 days, a day before the forecast starts, no budget set) is shown like `cannot_answer` and scored as a refusal.
- **Demo mode** (10a): Ask works on the demo data, offline by default, with example chips known to work. The LLM is used only if I turned it on and the key is present locally. Any future public deploy has the LLM off.
- **My real-data check** (11a): a read-only check command and a browser checklist, counts and yes/no only. Results stay in chat: Ask accuracy on my account is not on the "may be public" list.

## Out of scope
- Sending any result, row, amount, balance or merchant name to the LLM; LLM-written answer sentences.
- An `explain` block for "why did you warn me?" (Needs a look already shows that evidence).
- Sending the merchant list to the LLM, even opt-in.
- A form or dropdown plan builder.
- Follow-up questions that rely on the previous one; storing question history.
- Answers in French (the bilingual interface was put off until after v1).
- Advice, opinions and anything not in my data (these get "I can't answer that yet" plus examples of what it can answer).
- Charts in answers (a number or a table only).
- Running model-written code of any kind: a plan is data that is checked, never executed as code.

## Definition of done
1. Every block has unit tests with answers worked out by hand on small synthetic data, including refunds, transfers, an empty period and a period past the end of the data.
2. Plan checks refuse:
   - more than 10 steps
   - a step that uses a later or unknown name
   - a type mismatch
   - an unknown field or category
   - a forecast date more than 30 days past the data

   Each has a test.
3. "How I worked it out" is generated from the checked plan by code (a test shows the LLM's free text never reaches the page).
4. The `forecast`, `whatif`, `budget` and `safe_to_spend` answers equal the Forecast page's figures (the what-if: its what-if engine, see the step 3 note), the Budgets tab's and Home's for the same data (tests on synthetic personas).
5. Merchant matching: exact, alias, typo, several close matches (asks back) and no match all have tests.
6. The offline parser answers all its shapes in English and French; other questions get the honest refusal plus examples.
7. A test shows the LLM request contains only my question text (sent as I typed it, so it may contain merchant names or amounts I wrote myself), the category list and the plan format: nothing from my data (no rows, amounts, balances, dates or merchant names from the data). When the LLM is on, the Ask page says "Your question is sent as you typed it."
7b. A test shows the retry error message sent to the LLM never contains amounts, dates, balances or merchant names from the data.
8. The Ask section works on the demo data with the LLM off. The example chips all give answers.
9. 200 development questions written; the persona sheet given to me; the offline parser and the LLM planner scored on development.
10. Held-out: 100 questions (two independent question writers) and two independent gold-plan sets written into the blocked folder; disagreements reviewed by me; SHA-256 committed; the hook refuses the coding session's reads of the folder (tested).
11. The pass rule (this spec) is in a commit before the scored run; one held-out run; the result with n in DECISIONS and the README; setting offered or not as the rule says.
12. A read-only check command prints counts and yes/no only.
13. Reviewer PASS and merge gate PASS before each merge.
